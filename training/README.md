# eri-brain training — the no-teacher fine-tuning pipeline

This directory holds the **training path** for eri-brain (the hosted open model that is eri's
primary engine). It produces **LoRA/QLoRA adapters** that are served via vLLM multi-LoRA on the
quantized base. It is *not* the serving path (AWQ/FP8 serving-quant lives in `infra/eri-brain`).

Authoritative design: [`../docs/architecture/personalization-learning-loop.md`](../docs/architecture/personalization-learning-loop.md)
(the "Training approach: NO teacher" section is binding) and [`../docs/adr/0004-hosted-eri-brain-inference-tier.md`](../docs/adr/0004-hosted-eri-brain-inference-tier.md).

---

## HARD RULE — no teacher, no Claude/GPT, ever

> **eri trains its OWN model directly on clean data. It does NOT distill any teacher.**

- **Never** train on Claude or GPT outputs — including **eri's own Claude-on-CLI traces**. Those
  traces serve the user at runtime; they are *walled off* from the training corpus.
- **Not even a permissive teacher.** No DeepSeek-R1/Qwen distillation either. The student
  (Qwen eri-brain) learns from data, not from another model's generations done *for this purpose*.
- **The gate is PROVENANCE, not the license tag.** An "MIT"-licensed dataset that was generated by
  GPT-4 is tainted and off-limits. Every dataset must be **human-written** or **open-model-generated**
  (e.g. Mixtral/DeepSeek/Qwen as the *original authors of that public dataset*, not run by us to
  distill). Every eri-specific example must be **authored fresh** by us — never copied from a
  frontier model's output.

`validate.py` enforces this: it rejects any dataset not marked `human` or `open-model`, rejects
anything on the `OFF_LIMITS` list, requires every **generated** `eri_data/` record to carry
`meta.provenance == "open-model"`, and lints every example so the assistant never leaks a
tool/service name to the user (the invisibility rule).

### Generated by open models, not by Claude

The eri-specific training examples are **generated fresh by OPEN models** — `generate_eri_data.py`
drives Kimi K2.7 Code (Moonshot API) or a local Qwen/DeepSeek (Ollama). The generated text IS the
open model's output, so it is provenance-clean by construction. **Claude only orchestrates** the
pipeline; it never authors a training example. The `seeds/*.jsonl` are Claude-authored *structural
scaffolding* (schema shape) — they are NOT training data and are never trained on (see
[`seeds/README.md`](seeds/README.md)).

## Why no teacher (the rationale)

1. **ToS.** Claude and GPT both ban industrial distillation (Feb 2026). Building the moat on a
   ToS-violating corpus is a legal and existential risk.
2. **Ownership + provenance-clean by construction.** Train directly on permissive, clean-provenance
   data and on examples we wrote ourselves → the corpus is fully owned and auditable. No "is this
   tainted?" ambiguity later.
3. **Simpler.** No teacher-inference cost, no synthetic-pair construction. Existing open SFT corpora
   already cover chat, tool-calling, and restraint; we only author the small eri-specific slice.

## Dataset mix

Two sources combine into one SFT corpus:

### A. Clean-provenance public datasets (`datasets.yaml`)
Every entry is `human` or `open-model` provenance AND permissively licensed. Grouped by role:

| role | datasets | purpose |
|---|---|---|
| `chat` | oasst2, databricks-dolly-15k, allenai/tulu-3 (open-model/human slices only) | general helpfulness, instruction following |
| `tools` | glaiveai/glaive-function-calling-v2, Team-ACE/ToolACE, NousResearch/hermes-function-calling-v1, Salesforce/xlam-function-calling-60k | multi-step function/tool calling |
| `restraint` | nvidia/When2Call, xlam irrelevance split | when NOT to call a tool (cuts needless calls 60-83%) |
| `persona` | google/Synthetic-Persona-Chat, HuggingFaceTB/everyday-conversations, PersonaChat | warmth, natural texting register |

`datasets.yaml` also carries an explicit `OFF_LIMITS` list (GPT/Claude-distilled or NC-licensed sets
— APIGen-MT-5k, ToolBench, UltraChat, OpenHermes-2.5, Orca, Capybara, No-Robots, WildChat assistant
turns, etc.). `validate.py` fails if any manifest entry collides with it.

### B. eri-specific examples — GENERATED by open models (`eri_data/*.jsonl`)
There is no off-the-shelf set for the eri-specific slice, so we **generate it fresh with OPEN
models** (never Claude/GPT). The messages schema is
`{"messages":[{"role": "...", "content": "..."}], "meta": {"generator": "...", "provenance": "open-model"}}`.

`seeds/*.jsonl` (Claude-authored, **NOT** training data) anchor the *shape* of each category;
`generate_eri_data.py` feeds them to the open model as structural few-shot scaffolding and the model
produces the actual examples:

- `meta_tools` — the Composio meta-tool flow
  (`COMPOSIO_SEARCH_TOOLS → COMPOSIO_GET_TOOL_SCHEMAS → COMPOSIO_MULTI_EXECUTE_TOOL → natural answer`).
- `persona` — eri's voice (warm, concise, texting register; never names tools/services).
- `restraint` — answer directly from knowledge/memory; don't over-call tools.
- `routing` — the build vs control vs answer vs chat mode feel (supports the intent router).

`eri_data/` ships **empty** (`.gitkeep`); you populate it by running the generator (below). Every
generated record is validated (schema + invisibility + `open-model` provenance) and de-duplicated
before it is written.

## The generator fleet (`generate_eri_data.py`)

Multi-backend, all OpenAI-compatible `/v1/chat/completions`; one shared client path, only
base/key/model differ. **No teacher, no Claude/GPT — open models only.**

| backend | model (`--model`) | endpoint | notes |
|---|---|---|---|
| `moonshot` | **Kimi K2.7 Code** (`kimi-k2.7-code`, default) | `MOONSHOT_BASE_URL` (default `https://api.moonshot.ai/v1`), key `MOONSHOT_API_KEY` | top agentic open model; the user authorizes use of their Kimi/Moonshot subscription via API. The generated text is **Kimi's** output (clean provenance). |
| `ollama` | **Qwen2.5-72B** (`qwen2.5:72b`, default) or **DeepSeek-R1-32B** (`deepseek-r1:32b`) | `http://localhost:11434/v1`, no key | fully local; `ollama pull qwen2.5:72b` / `ollama pull deepseek-r1:32b` first. |

**Hard provenance guard:** the script REFUSES any base URL pointing at `anthropic`/`openai` — the
generator must be an open model. The default backend is `ollama` (local, $0).

```bash
# dry-run: build the prompts + print the plan, NO network call, no key needed
python3 training/generate_eri_data.py --dry-run --backend ollama

# local open model (Ollama) — one category
python3 training/generate_eri_data.py --backend ollama --model qwen2.5:72b --category meta_tools --count 50

# Kimi K2.7 Code via Moonshot (the user's subscription)
export MOONSHOT_API_KEY=...   # required for moonshot (not for --dry-run / ollama)
python3 training/generate_eri_data.py --backend moonshot --model kimi-k2.7-code --category all --count 100
```

Flags: `--backend {moonshot,ollama}` · `--model` · `--base-url` (still guarded) · `--category
{meta_tools,persona,restraint,routing,all}` · `--count N` · `--out DIR` · `--dry-run` · `--self-test`.
Each record is stamped `"meta":{"generator":"<backend>:<model>","provenance":"open-model"}` so the
corpus is auditable.

## LoRA / QLoRA + quantization plan

- **Training:** QLoRA SFT (HF PEFT + TRL `SFTTrainer`). The base is loaded **4-bit (bnb nf4,
  double-quant)** so a single mid-size GPU can fine-tune a 32B model; LoRA adapters train in
  bf16 on top. Config in `config.yaml` (rank/alpha/dropout/target-modules), model-agnostic via
  `model.base_id`.
- **Objective:** start with **SFT** on the mixed corpus (this directory). The self-improvement
  loop later adds **KTO** (binary kept/edited/rejected signals) per-user/cohort — same LoRA
  machinery, different objective.
- **Serving (separate path):** the resulting LoRA adapters are served via **vLLM multi-LoRA** on a
  base that is quantized for *serving* with **AWQ/GPTQ-INT4 or FP8** (vLLM ≥ 0.15 for MoE
  multi-LoRA). That serving-quant is `infra/eri-brain`'s job, NOT this file. Training-quant (bnb)
  and serving-quant (AWQ/FP8) are deliberately different.

## Two training backends

There are **two** ways to LoRA-train the eri-brain. Pick by hardware:

| backend | file | hardware | quant | when |
|---|---|---|---|---|
| **MLX-LM** (Apple-native) | `prepare_corpus.py` → `mlx_finetune.py` | **Apple Silicon** (M-series, e.g. M5 Max / 128GB) | MLX 4-bit (`mlx-community/Qwen3-32B-4bit`) | **local on a Mac** — bnb/CUDA won't run here |
| **HF PEFT + bitsandbytes** | `lora_finetune.py` | **NVIDIA CUDA GPU** | bnb 4-bit nf4 QLoRA | cloud/datacenter GPUs |

Both train the **same Qwen3-32B**, the **same clean corpus**, and the same no-teacher provenance
rule. They differ only in the kernel/quant stack. The MLX path is the default for local Mac work.

---

## MLX-LM path (Apple Silicon — Qwen3-32B on an M5 Max)

Apple's [`mlx-lm`](https://github.com/ml-explore/mlx-lm) LoRA-trains on the Metal GPU via unified
memory. bitsandbytes (the CUDA path's quantizer) does **not** run on macOS, so this is the native
alternative for fine-tuning Qwen3-32B locally.

### Install

```bash
pip install mlx-lm          # Apple Silicon only; brings in mlx
pip install pyyaml          # optional: lets mlx_finetune.py read LoRA params from config.yaml
                            #   (without it, it falls back to the same defaults: rank=16 scale=2.0 dropout=0.05)
```

### Flow

```bash
# 1. PREPARE the corpus. Merges eri_data/ + eri_data_local/, validates (provenance + invisibility +
#    schema, dropping invalids), de-dups by SHA-256 of the normalized messages, converts to the
#    MLX-LM chat/tools format, and writes mlx_data/{train,valid}.jsonl (95/5 split).
python3 training/prepare_corpus.py --dry-run        # plan only; no files written, stdlib only
python3 training/prepare_corpus.py                  # writes mlx_data/{train,valid}.jsonl
#   python3 training/prepare_corpus.py --probe-open      # stream 1 row/dataset through each converter;
#                                                        #   prints OK/FAIL + roles (fast verification, tiny download)
#   python3 training/prepare_corpus.py --with-open 200   # ALSO blend 200 rows/dataset from datasets.yaml
#                                                        #   (needs HF `datasets`; OFF_LIMITS + GPT/Claude slices excluded;
#                                                        #    gated sets e.g. xlam-60k need HF_TOKEN; skipped if absent)

# 2. DRY-RUN the trainer — validates mlx_data/, writes the generated mlx_lm config, and prints the
#    EXACT mlx_lm.lora command. NO model download, NO GPU-hours.
python3 training/mlx_finetune.py --dry-run

# 3. TRAIN (Metal GPU) — downloads mlx-community/Qwen3-32B-4bit (~18GB) ONCE, then LoRA-trains.
#    This takes HOURS on a 32B. Same command, minus --dry-run:
python3 training/mlx_finetune.py
#   (equivalently: python3 -m mlx_lm lora --config training/mlx_data/lora_config.yaml)
```

### MLX chat-format conversion (how tool calls are handled)

eri's records already use the messages schema mlx_lm expects, so the converter (`prepare_corpus.py`)
keeps tool calls **structured** rather than flattening them into assistant text:

- `messages` is passed through; only mlx-recognized keys are kept
  (`role`/`content`/`tool_calls`/`tool_call_id`/`name`). eri's internal `meta` block (which carries
  provenance) is **dropped from the trainer input** — provenance is enforced at the validation gate,
  not shipped into the model's context.
- Assistant turns with `tool_calls` keep `function.name` + the JSON-**string** `arguments` exactly as
  mlx_lm's tools format documents; the Qwen chat template renders the tool call. `role: "tool"`
  replies (with `tool_call_id`) pass through unchanged. An optional top-level `tools` array is
  passed through if a record carries one.

This matches mlx_lm's documented chat/tools JSONL format directly — no Qwen-template hand-rendering
needed.

### Base model

Defaults to **`mlx-community/Qwen3-32B-4bit`** (the Apple-native 4-bit build mlx_lm loads directly;
fits a 32B in unified memory and trains in hours). `config.yaml`'s `model.base_id` is `Qwen/Qwen3-32B`
for the CUDA path; `mlx_finetune.py` auto-prefers the 4-bit MLX repo unless you pass `--model`.

### LoRA param mapping (config.yaml → mlx_lm)

| config.yaml | mlx_lm | note |
|---|---|---|
| `lora.r` | `lora_parameters.rank` | |
| `lora.alpha` (+`r`) | `lora_parameters.scale` | mlx_lm uses `scale = alpha / rank` (32/16 = 2.0) |
| `lora.dropout` | `lora_parameters.dropout` | |
| `lora.target_modules` | `num_layers` (default 16) | mlx_lm applies LoRA to the top *N* transformer blocks rather than naming HF projections; the HF target set is surfaced as informational |

### Adapter output + chatting with the result

The LoRA adapter lands in **`training/adapters/eri-v1/`** (override with `--adapter-path`). Chat with
the trained adapter:

```bash
python3 -m mlx_lm generate \
  --model mlx-community/Qwen3-32B-4bit \
  --adapter-path training/adapters/eri-v1 \
  --prompt "hey eri"
```

`prepare_corpus.py --dry-run`, `prepare_corpus.py --self-test`, and `mlx_finetune.py --dry-run` are
part of the **green gate** — they run with stdlib only (no mlx, no GPU, no network). `mlx_data/` and
`adapters/` are gitignored generated artifacts.

## How to run (CUDA / PEFT path)

```bash
# 0. one-time deps. The validator + both dry-runs need NOTHING beyond stdlib (pyyaml is OPTIONAL —
#    without it the datasets.yaml/config.yaml parse checks are skipped, not failed). The generator is
#    stdlib-only. Only real training needs the heavy stack.
pip install pyyaml                       # optional: enables the datasets.yaml/config.yaml checks
pip install torch transformers peft trl datasets bitsandbytes accelerate   # for real training only

# 1. VALIDATE — no GPU, no network, no weights. Fails loud on any provenance/schema/invisibility issue.
#    Runs anywhere (stdlib core). With pyyaml it also checks datasets.yaml + config.yaml.
python3 training/validate.py

# 2. GENERATE eri_data with an OPEN model (never Claude/GPT). Validates + dedups before writing.
#    --dry-run builds the prompts and makes NO network call.
python3 training/generate_eri_data.py --dry-run --backend ollama            # plan only, no network
python3 training/generate_eri_data.py --backend ollama --category all --count 50      # local
#   export MOONSHOT_API_KEY=... ; python3 training/generate_eri_data.py --backend moonshot --category all --count 100

# 3. RE-VALIDATE the now-populated corpus.
python3 training/validate.py

# 4. DRY-RUN the trainer — validates config + manifest + eri_data and prints the planned run.
python3 training/lora_finetune.py --config training/config.yaml --dry-run

# 5. TRAIN (GPU) — same command without --dry-run. Loads the base 4-bit and runs QLoRA SFT.
python3 training/lora_finetune.py --config training/config.yaml
```

Full flow: **prepare datasets → generate eri_data (open models) → validate → QLoRA train.**

`validate.py`, `generate_eri_data.py --dry-run`, and `lora_finetune.py --dry-run` are the **green
gate**: they run anywhere (no GPU/network/key), and CI should block on them. Heavy imports
(torch/peft/trl) and the actual backend calls are guarded behind the non-dry-run paths.

## Layout

```
training/
  README.md            # this file
  datasets.yaml        # commercial-safe, clean-provenance dataset manifest + OFF_LIMITS
  config.yaml          # model id (Qwen), LoRA params, quant, training args
  generate_eri_data.py # multi-backend OPEN-model generator (Kimi/Ollama); --dry-run = no network
  prepare_corpus.py    # MLX path: merge eri_data(+_local) + dedup + validate + convert to MLX chat
                       #   format -> mlx_data/{train,valid}.jsonl; --dry-run/--self-test = stdlib only
  mlx_finetune.py      # MLX path: LoRA-train Qwen3-32B via mlx_lm.lora (Apple Silicon); --dry-run = no GPU
  lora_finetune.py     # CUDA path: QLoRA SFT via PEFT + TRL SFTTrainer; --dry-run validates without a GPU
  validate.py          # STDLIB-ONLY validator + self-check (provenance/schema/invisibility); pyyaml optional
  seeds/               # SEED TEMPLATES — Claude-authored structural scaffolding, NOT training data
    README.md          #   (explains: seeds are shape-only, never trained on)
    meta_tools.jsonl   #   shape of the Composio meta-tool flow
    persona.jsonl      #   shape of eri's voice / tone
    restraint.jsonl    #   shape of "answer without a tool"
    routing.jsonl      #   shape of build/control/answer/chat mode feel
  eri_data/            # GENERATED training data (open-model provenance) — starts EMPTY (.gitkeep)
    .gitkeep           #   populated by generate_eri_data.py: <category>.jsonl per category
  eri_data_local/      # GENERATED by LOCAL open models (qwen2.5:72b / deepseek-r1:32b); merged + deduped
  mlx_data/            # GENERATED (gitignored): MLX chat-format train.jsonl/valid.jsonl + lora_config.yaml
  adapters/            # GENERATED (gitignored): mlx_lm.lora output, e.g. adapters/eri-v1/
```
