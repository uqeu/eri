1Overview & product

eri is an agentic AI IDE: the user describes what they want in natural language (or voice), and eri builds/edits real apps, learning the user's preferences over time. Positioning is "agentic + personalized + learns about you" - never literal "AGI". The model strategy is a two-engine split:

Mercury

Fast lane - instant edits

Inception Labs diffusion model (mercury-2). Sub-second surgical single-file edits via SEARCH/REPLACE. Effectively free at provider level (<$0.005/turn); metered as turns, not tokens.

Claude

Builder lane - real work

Anthropic Sonnet for full builds, multi-file work, and reasoning. Metered against the plan's token budget. Opus blocked on the shared proxy by cost-guard.

Each paid plan ships a Claude token allowance + a Mercury turn allowance ("eri credits"). See Billing.

Engine routing (locked) - split by surface + shape, not just fast-vs-deep: Mercury can't tool-call, so it can't drive an agentic loop - its home is IDE live edits (Cmd-K / inline / quick-fix), turn-metered. The agentic tool-use loop is intrinsically Claude-shaped, so the CLI is Claude-only (builds / iterations / plans), token-metered. A mode picker (like the big labs) selects the Claude tier in the CLI - --mode fast (Haiku) / thinking (Sonnet, default) / auto - not Mercury-vs-Claude; the IDE gets an Instant / Thinking / Auto toggle. See 8b.

5Auth

Web - Google OAuth + JWT

Google OAuth → short-lived JWT access token + single-use rotating refresh token. Client: website/lib/auth-client.ts (single-flight refreshSession to avoid races). Server verify: userFromBearer() in website/lib/auth.ts - JWT only.

CLI / device - RFC 8628 Device Authorization Grant

The correct, race-proof flow (rebuilt 2026-06-04). Two distinct codes:

CLI→ POST /start device_code (secret)+user_code (public)
browserenters user_code → POST /approveissue api_token, set pending_secret
CLIPOST /poll {device_code} →token (idempotent until expiry)
  • device_code: 256-bit secret, only the polling client holds it, never in the browser/URL. The token endpoint key.
  • user_code: short (XXXX-XXXX, Crockford base32), shown in the browser, used to approve. Cannot redeem the token.
  • Idempotent delivery: /poll returns the token on every poll until the grant expires (10 min) - kills the single-delivery race where a duplicate poll consumed the one-shot secret.
  • Routes: website/app/api/v1/auth/device/{start,approve,poll}/route.ts; CLI: crates/eri_cli/src/auth.rs; lookups in website/lib/inference/db.ts.

Inference verify uses a different verifier: authenticateApiBearer() (website/lib/auth/api_tokens.ts) accepts the eri_sk_ api_token. userFromBearer (JWT) rejects api_tokens - that's why /poll returns identity (email/tier) so the CLI can show who's signed in without a JWT-only call.

6bPricing & economics

Every user request hits our master key, so we pay the provider. The user's bucket budget bounds their consumption = bounds our cost. The margin is only safe if revenue-per-token > provider cost-per-token. Provider rates as of 2026-06; verify against the live pricing pages before changing tiers.

How eri counts tokens

  • Pre-flight estimate (the gate): estimateTokens(body) in lib/inference/tokens.ts ~ chars/4. Used only by ensureWithinQuota to refuse obviously-over requests before calling the model.
  • Actual (what's billed): extractUsage(provider, payload) pulls real tokens_in + tokens_out from the provider's usage object - Anthropic message_delta.usage.{input_tokens,output_tokens} from the SSE stream, captured in countStreamUsage. recordUsage() then increments token_buckets.tokens_used by tokens_in + tokens_out.
  • Unit today = 1 raw provider token, in or out, counted 1:1. cost_usd_micros is computed (price table) for observability but is not used for billing.
  • Mercury is not token-billed: bill:false, metered as one mercury_turns_used per call.

Margin per tier - and the Pro+ risk

Counting in+out 1:1 ignores the 5x output multiplier. At the worst case (output-heavy), a tier priced near $15 / 1M tokens of revenue can break even or lose money against Sonnet's $15/M output rate.

Mitigations (recommended, in priority order)

  1. Weighted "eri credits" instead of raw 1:1 tokens. Deduct tokens_in + OUTPUT_WEIGHT x tokens_out (e.g. weight 3-5) so the bucket maps to real $ cost and output-heavy builds can't blow margin. One-line change in recordUsage + show "credits" in the wire.
  2. Prompt caching on Claude. Add cache_control to the system prompt + large file blocks; agentic re-sends then cost ~90% less on input. Biggest absolute saving for builds.
  3. Mercury-first routing. Single-file edits and small diffs go to Mercury ($0.25/$0.75, ~free) via /iterate; reserve Claude tokens for genuine multi-file builds + reasoning. This is the core two-engine economic advantage.
  4. Hard output cap + turn cap per build so a runaway agent can't burn a month of budget in one prompt.
  5. Re-price Pro+/Teams to keep revenue-per-token above ~$9/M (the 1:1 blended floor) with comfortable margin, or lower their included allowance.

7Inference

The metered proxy is the heart of the system and is already production-grade.

runProxy - the metered passthrough reuse as-is

website/lib/inference/proxy.ts. Each /api/v1/inference/<verb> is a one-liner calling runProxy. It:

  1. Auths the api_token bearer; per-token rate-limits.
  2. Forwards the full request body verbatim → Anthropic tools/system/messages/stream all pass through. Tool-use works.
  3. Cost-guard (blocks Opus/o1/gpt-5-pro), quota gate (402 + ghost), master-key injection.
  4. Captures real usage from the SSE stream (countStreamUsage → parseUsageFromSSEFrame, incl. Anthropic message_delta.usage) and records it. BYOK fallback (x-eri-byok) skips quota/billing.

8Code-gen - current state

The problem. Two disconnected paths, neither correct.

Path A - local Mercury

eri build/iterate → MercuryBackend (Rust). writes files via write_file/apply_search_replace_blocks unmetered needs local MERCURY_API_KEY, bypasses plan budget. ("build key not set" error.)

Path B - metered relay

Existing apply primitives to reuse: crates/eri_control/src/eri_control.rs → apply_patch_to_disk(), write_build_files(); crates/eri_inference/src/eri_inference.rs → apply_search_replace_blocks(), parse_search_replace_blocks().

8bTarget - client-side agentic loop

The Claude Code / codex pattern (learned from public OAuth + agent-loop standards, not their source): the agent loop runs in the CLI, which owns the workspace and executes tools; the backend is a stateless metered inference proxy (runProxy, already built).

CLImessages + tools → /inference/messages (metered)→ Claude tool_use→ CLI executes locally→ tool_result, loop
  • CLI tools (path-jailed to workspace): list_dir, read_file, write_file, str_replace, done - executed via eri_control + apply_search_replace_blocks.
  • Claude builds → /inference/messages (token-billed). Mercury fast edits (eri iterate) → /inference/iterate (turn-metered).
  • Loop sends running messages each turn (server stateless), caps turns (~24), handles 402/403/ghost gracefully.
  • System prompt = .eri/agents/builder.md (the "cracked" quality bar) adapted to the tool protocol.
  • New module: crates/eri_cli/src/build_agent.rs. /api/v1/agent/run retires for tool work.

8cAgent capability layer - what eri subsumes

Competitive read: a wave of YC tools (Nia/Nozomio $6.2M, Exa, Context7, Greptile, Cursor's index, v0/Lovable/Bolt builders) each sell one slice of the agent loop - retrieval, deep research, codebase index, doc Q&A, or generation - as a separate product an agent bolts on via MCP. eri's wedge is to own the whole loop inside the IDE and have it learn about you (the personalization tier), so these are internal capabilities, not integrations to pay for. Arlan (Nia) names the real vision himself: "agents that get better the more you use them" - that is eri's product, at the IDE level.
