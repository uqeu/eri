ARK · Architecture Review

Deepening opportunities

Where ARK's live code is shallow — an interface nearly as complex as the implementation behind it — or where a seam leaks. The aim is testability and AI-navigability: turn many small modules into fewer deep ones. Reviewed the live pipeline only (Stage 1/2/3, World Model V3, the narrator, forensic, deviation) — dead/archived dirs excluded.

deletion test · a module earns its keep if deleting it makes complexity reappear across N callers, not vanish.

01DetectionStack — a shallow multiplexer over ten detectors

Strong

Files

cloud/stage2/detection_stack.py:100-552

Problem

One process_clip(frames) → DetectionBundle interface hides ~840 lines: ten detector wrappers (pose, objects, ST-GCN++, gait, posture, micro, hand-object, emotion, gaze, Lumen), ten loaders, an inline Ultralytics adapter, and the per-camera feature toggles scattered across nine call sites. Adding or swapping a detector means editing the stack and the PersonDetection dataclass. Tests must patch both _run_X and _load_X.

Solution

Make each detector a self-contained adapter behind one small interface (load() · process(frames) → modality tokens), registered in a detector registry. process_clip becomes an orchestration loop over the enabled set; feature-toggle logic lives in one place. The caller's interface is unchanged.

Benefits

Locality: each detector's quirks live in one file, not interleaved in an 840-line method. Leverage: swapping Pose / adding a modality is a one-file change. Test surface: one fake adapter tests the orchestration; each adapter tests in isolation.

02The narrator trio — Conductor × GemmaRunner × GemmaVLMService

Strong

Files

engine/vlm/conductor.py · engine/vlm/gemma_runner.py · engine/vlm/gemma_vlm_service.py

Problem

Three modules each own model load (MLX-vs-transformers), caching, and inference, with overlapping responsibilities and different strategies: GemmaRunner caches by (image,prompt) with a 5 s TTL; ConductorBrain (a separate Llama) caches nothing and re-generates live. A caller can't tell when to call GemmaVLMService.analyze_sync vs ConductorBrain.evaluate_window, and neither model is injectable for tests (you mock self._model or trust the heuristic fallback).

Solution

Extract one LlmBackend protocol (generate(prompt, max_tokens) → str) with caching + telemetry built in; have both the Gemma path and the Conductor use it instead of owning model load. Move cooldown/cache tuning into one InferenceScheduler. Mirrors the clean LlmBrain protocol the forensic stack already uses — this is that pattern, applied to the live narrator.

Benefits

One cache strategy (no redundant Conductor calls on identical captions); model swaps (Qwen→Gemma-26B-Thinking) become a backend change; the reasoning logic becomes testable with a fake backend.

03Sustained-behaviour prompt leaks across the Stage-2 ↔ omni seam

Worth exploring

Files

cloud/stage2/worker.py:689-696, 873-940 · cloud/stage2/vlm_client.py:286-319 · cloud/omni/engine/alert_schema.py

Problem

The worker reaches across a seam to know narrator concerns: it lazily imports build_sustained_behavior_prompt() from cloud.omni, formats the narration (_format_sustained_narration), and the JSON→SustainedBehaviorFact parsing sits inside the client. The prompt shape lives server-side; the formatting lives in the worker — two places that can drift.

Solution

Give VlmClient a narrate_sustained(crops, context) → SustainedBehaviorFact that owns the prompt, the parse, and the human-readable formatting. The worker supplies only the detector context dict (it already builds one). The omni coupling and the drift both disappear.

Benefits

Prompt changes never touch the worker; the parse is unit-testable in isolation; narration format lives in one place. Note: I built this seam earlier this session — it works, this is a tidy-up, not a rescue.

04ark_deviation — over-split internals, weights hard-coded as Python

Worth exploring

Files

ark/ark_deviation.py:54-342

Problem

ConceptBottleneck and FreeEnergyComputer are stateless math + ~110 lines of domain-knowledge weight dicts, never used outside ArkDeviationEngine.__init__. The split adds indirection without encapsulation, and the Welford precision-learning is bolted onto the calculator (an optimizer living inside the thing it optimizes). To unit-test concept classification you must build the whole engine.

Solution

Lift the weights to a tunable config (JSON/dataclass), merge the two calculators into one stateless FeatureAnomalyScorer.score(subject, weights) → DeviationResult, and split precision-learning into a PrecisionCalibrator that wraps it.

Benefits

One clear public API; weights an operator can tune without code; scorer + calibrator each test in isolation.

05WorldModelLoopV3 — the four-provider constructor shotgun

Speculative

Files

engine/world_model/v3/loop.py:79-115

Problem

The constructor takes four optional providers (action / depth / gaze / lumen) each with a Null*Provider default — ignored entirely in the shadow-mode path. A caller reading the signature assumes all four are required; a fifth signal means the constructor grows again.

Solution

Minimal constructor (config, vlm, version); providers via register_provider(...), validated at step() only when actually needed.

Benefits

A clear "what do I need to run one frame?" contract; shadow mode tests with zero providers; extensible without touching the signature.

06Alert lifecycle ↔ sinks — transitions and durability aren't coordinated

Worth exploring

Files

cloud/stage2/alert_lifecycle.py · cloud/stage2/worker.py:437-501 · cloud/stage2/sinks/*

Problem

The state machine computes transitions; the worker separately writes them to S3 + Supabase + WebSocket with no atomicity. A Supabase upsert can land while the S3 clip fails; on SQS redelivery the lifecycle is rehydrated from Redis but may be stale. Partial-failure recovery is implicit in the retry path — there's no test for "Supabase ok, S3 failed".

Solution

An AlertEventRepository that owns the machine + sink fan-out as one unit: transition(...) → Result reports which sink failed; or make Supabase the write-ahead source of truth and treat S3/WS as derived views. Touches durability — change carefully, behind the existing tests first.

Benefits

State and persistence stay in sync; partial failure is explicit and testable; no two workers silently advancing one event.

Already deep — don't break these

  • cloud/stage2/person_clip.py & relative_anomaly.py — pure, immutable, one job, fully tested. Model depth-to-complexity.
  • world_model_client.py — tiny score(tokens) → PersonScore over the V3 forward pass. Clean seam.
  • ark/forensic/brain.py (LlmBrain Protocol) & ark_types.py — pluggable, never-raises, exhaustive frozen types.
  • conductor.py EntityTracker + EscalationThrottle — tight, deterministic, testable state machines.
  • redis_client.py — three disjoint concerns cleanly separated, clear fail-open semantics.
Top recommendation

Start with #01 DetectionStack → detector registry.

It's the highest-leverage and lowest-risk: the caller interface (process_clip → DetectionBundle) doesn't change, but every future detector swap or addition — and you have many (Pose, gait, a new modality) — becomes a one-file change instead of surgery on an 840-line method. It also unblocks honest per-detector tests. Pair it with #02 (one LlmBackend protocol) next: it kills the narrator-trio confusion and reuses the exact LlmBrain pattern the forensic stack already proved. Defer #06 (durability — real but riskier) until there's a failing-case test to anchor it.
