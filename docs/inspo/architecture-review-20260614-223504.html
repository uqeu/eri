Architecture Review · RunPod GPU-worker build

Is the RunPod build sound?

Short answer: the model roster is right and the plan is sound — but the inference seam isn't ready to package yet. There are two parallel pipelines, the API tier loads torch/ths in-process, weights resolve by machine-specific path literals, and the worker silently runs random weights if a file is missing. Fix those four and the RunPod packaging becomes clean.

Candidate 1

Split EngineInference: API tier calls the worker over HTTP

Strong

Files

  • ark/api/inference.py (EngineInference)
  • ark/api/server.py · DEPLOY.md
  • cloud/stage2/worker.py

Problem

EngineInference loads the ths detector stack + World Model in-process and only the narrator goes over HTTP. So the "light CPU API tier" (api.honoursystem.ca) would actually need torch + ths + a GPU — defeating the two-tier design in DEPLOY.md. The seam (InferenceBackend.analyze) is good; the prod adapter is in the wrong process.

Solution

Add a thin HttpEngineInference adapter: the API tier POSTs the analyze request to the RunPod worker and returns its JSON. The heavy EngineInference becomes the worker's implementation, not the API's. Same InferenceBackend interface — now with two adapters (Fake + Http) at the API tier, and the engine one living on the GPU.

Before
API host imports
ths + torch + WM
= GPU on the API tier
After
API → HTTP → worker
API host = fastapi+httpx
GPU only on RunPod

Benefits

  • leverage: the API tier deploys as the light image we already wrote — no torch.
  • locality: all GPU concerns live in the worker; the API never changes when the engine does.
  • tests: Fake at the API tier (done), the engine tested on the worker — the HTTP seam is the contract.
Candidate 2

One pipeline module behind both the SQS worker and the API

Strong

Files

  • cloud/stage2/worker.py · detection_stack.py
  • ark/api/inference.py (EngineInference)
  • engine/world_model/v3/loop.py

Problem

"Run detectors → World Model → gate → VLM" is implemented twice — once in the SQS worker.py, once in EngineInference. Two copies drift: a gate tweak or a new detector has to be made in both, and the RunPod worker would be a third copy.

Solution

Extract one analyze_clip(frames, opts) → Alert pipeline module. The SQS worker, the API's engine adapter, and the new RunPod handler all call it. Deletion test: delete it and the pipeline logic reappears in 3 callers — it earns its keep.

Candidate 3

A WeightResolver + fail-closed boot verify (no path literals, no silent random-init)

Strong

Files

  • engine/vlm/weights_manifest.py (E4B path)
  • engine/world_model/v3/loop.py (load_or_initialize)
  • ark/forensic/grounding.py (Eagle path)
  • ark/redaction/redact.py (abs paths)

Problem

Weights resolve by machine-specific literals: data/models/gemma/google_gemma-4-E4B-it, /Users/khai/Desktop/Eagle/Embodied, hardcoded redaction paths. And the WM loader looks for world_model_v3.pth while the trained file is world_model_latest.pth — a miss means it serves random weights with only a WARNING (the threat gate becomes noise). On RunPod none of those Mac paths exist.

Solution

One WeightResolver: every model resolved by a key → (HF id | registry path | env override), no literals. Plus a verify_weights() gate the worker runs at boot that refuses traffic unless every required weight is present, the right variant, and (for WM) non-random. Silent degradation → loud startup failure.

The safety win

Today a renamed checkpoint = a threat gate quietly outputting noise in production. verify_weights turns that into "the worker won't start," which is exactly what you want for a safety system.

Benefits

  • leverage: the same image runs on any box — paths come from config.
  • locality: "what weights does ARK need" answered in one manifest.
  • safety: no silent random-init, no missing-model surprises mid-incident.
Candidate 4

VLM serving = one seam; dev vs prod = adapters; thinking + safety centralized

Worth exploring

Files

  • engine/vlm/{weights_manifest,gemma_runner,backends,llm_backend}.py
  • engine/vlm/prompts.py (SYSTEM_PROMPT)

Problem

The VLM has a clean HTTP seam (backends.py already parses a thinking trace ✅), but the dev path (E4B / MLX / GGUF) and the prod path (vLLM 26B-A4B) are tangled across four files, and <|think|> isn't in the system prompt — so thinking (the proactive moat) won't actually fire unless it's added.

Solution

One VlmBackend seam, two adapters: local-dev (MLX/llama.cpp, E4B) and prod (vLLM HTTP, 26B-A4B-it). Centralize the <|think|> enablement + the safety-framed prompt so dev and prod can't diverge, with a thinking_token_budget for the officer fast-path.

Candidate 5

Serverless cold-start vs warm — don't put the officer path on a cold 16 GB model

Worth exploring

Problem

A RunPod serverless worker loading a 15-16 GB AWQ model + detectors has a multi-minute cold start. The architecture's <2 s officer path can't live on that. The spec already splits this — RunPod serverless for offline/batch, AWS ca-central warm GPU for real-time/Canadian — so the plan is sound if we honor the split.

Solution

Package offline (annotate-a-clip, forensic search, redact) for RunPod serverless — cold start is fine for batch. Keep real-time + officer on the always-warm GPU (with the idle-CPU auto-terminate alarm). Use a RunPod active worker / min-instances if you want warm offline too, at standing cost.

Top recommendation

Yes, RunPod is sound — but do C1 + C2 + C3 first, then build the handler.

The packaging only works once the pipeline is a single module (C2) reached through a single HTTP inference seam (C1), with config-resolved, boot-verified weights (C3). Then the RunPod handler is a thin wrapper around analyze_clip(), the API tier stays light, and the worker can never serve random or wrong weights. C4 (thinking + 26B-A4B) and C5 (cold vs warm) ride along.

1 · HTTP inference seam→ 2 · one pipeline module→ 3 · WeightResolver + verify→ 4 · VLM dev/prod adapters + <|think|>→ 5 · offline serverless / warm real-time→ RunPod handler (thin)

Verdict: the models we're uploading are correct (per the verified roster) and the two-tier plan is right. The risk isn't what we upload — it's that the inference code isn't packaged as one clean seam yet. Fix C1-C3 and the build is solid.
