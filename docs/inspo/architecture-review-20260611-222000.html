The ControlTurn seam, after the keystone landed

The computer-control loop is now provider-agnostic: drive_control_loop runs through the ControlTurn seam with two adapters (ClaudeControlTurn, LocalControlTurn), local-first selection, and per-goal escalation. Two adapters = a real seam. This review looks only at the code that just shipped, and asks where it is still shallow — interface nearly as complex as the implementation — and where a small deepening would buy locality + test surface.

1 · The self-improvement sink is invisible to tests

Strong

Files: control_turn.rs (record_control_turn), control_agent.rs (drive_control_loop)

Problem: record_control_turn is the sink for Candidate B — the whole point of instrumenting the turn is the self-improvement log. But it does if cfg!(test) { return; } to keep the loop's tests free of filesystem side effects. So the only verified part is the pure control_turn_log builder; whether the loop actually records the right thing on the right turns is untested by construction. Behaviour differs between test and prod — the classic smell that hides the real bug (does escalation get logged? does a no-tool answer?).

Solution: make the sink a seam, not a cfg! branch. A ControlTurnSink trait with two adapters — MemorySink (prod, writes to the learn-do store / later eri_graph) and a recording double in tests. The loop calls sink.record(log); tests assert the sequence of records. The cfg!(test) guard disappears.

Benefits: the instrumentation gains locality (one place defines what a control turn records, exercised the same way in test and prod) and a real test surface — the routing-learning loop can't silently rot. Leverage: the same sink seam is exactly where eri_graph causal logging plugs in later, with no loop change.

Before — cfg branch
fn record_control_turn(..) {
  if cfg!(test) { return; }   // ← untestable
  let log = control_turn_log(..);
  MemoryStore::open()…insert(log)
}
// tests verify control_turn_log ONLY,
// never that the loop calls it correctly.
After — injected sink
trait ControlTurnSink { fn record(&self, l: ControlTurnLog); }
struct MemorySink;   // prod
struct RecordingSink(Mutex<Vec…>);  // tests

loop: sink.record(control_turn_log(engine, goal, &out));
// test: assert recorded == [local→escalate, claude→open_app, …]

2 · drive_control_loop wears its dependencies as 8 positional params

Worth exploring

Files: control_agent.rs (drive_control_loop, run_control_agent)

Problem: the loop carries #[allow(clippy::too_many_arguments)] — engines, bridge, gate, confirm, system, tools, goal, max_turns. Most are static for the session (engines/bridge/gate/system/tools never change across the run); only goal/confirm/max_turns vary per invocation. The signature can't tell you that. Adding the sink from Candidate 1 makes it 9.

Solution: a ControlSession deep module that owns the static wiring (engines + bridge + gate + system + tools + sink) and exposes drive(goal, &mut confirm, max_turns). The loop body is unchanged; the interface shrinks to one verb over a configured session.

Benefits: leverage — callers see "a session you can drive," not a 9-tuple. Locality — the local-first/escalation wiring is assembled once in the constructor, not re-passed. Deletion test: deleting ControlSession scatters that assembly back across run_control_agent + every test. It concentrates complexity → it earns its keep.

3 · The local model's tool arguments don't match the spec keys

Worth exploring

Files: control_turn.rs (parse_local_tool_calls) → control_agent.rs (parse_action)

Problem (live-observed): qwen2.5:1.5b, asked to "open Safari", correctly emits an open_app tool call — but with {"app_name":"Safari"} instead of the spec's {"name":"Safari"}. parse_action is strict (s("name") → error), so the local turn that chose right still fails downstream. This is the handoff's thesis in miniature: small models are good at deciding, weak at exact structure — "the real work is structured output, not a bigger model."

Solution: not a leniency patch on parse_action (that's shared with the cloud path, which gets keys right). Instead, a thin local argument-normalisation step at the LocalControlTurn seam — a tiny per-tool alias map (app_name|application → name, …) applied only to local tool calls, plus a stricter local system-prompt that pins the exact schema. This belongs to the deferred 50-task eval / structured-output hardening phase, where it can be measured.

Benefits: keeps the strict shared parse_action honest while absorbing small-model sloppiness at the one seam that owns it. Test surface: alias-normalisation is a pure function — table-tested against recorded local outputs.

Before
local → {"app_name":"Safari"}
parse_action("open_app") → s("name") = None
→ Err "open_app needs name"  ✗ correct choice lost
After
local → {"app_name":"Safari"}
normalise_local_args("open_app") → {"name":"Safari"}
parse_action → OpenApp("Safari")  ✓

Top recommendation

Start with Candidate 1 (the sink seam). It's the only Strong item because it closes a correctness gap, not just an ergonomic one: the self-improvement log is the entire reason the turn is instrumented, and right now its behaviour is verified nowhere. Two adapters (memory + recording double) make it a real seam and delete the cfg!(test) smell. Candidate 2 pairs naturally — once a sink is a 9th dependency, ControlSession is the right place to put it — so do them together. Candidate 3 is real but belongs to the eval phase where structured-output quality is measured, not guessed.
