Is eri SOTA software? — the honest read

Four read-only passes over the landscape: the brain (router + inference + local engine), the agent harness (build + control), the workspace macro-structure (30+ crates), and the cloud + surfaces (proxy, auth, app, IDE). Verdict up front, then the deepening candidates.

The verdict

The design is genuinely SOTA-competitive. The agent seams (the new provider-agnostic ControlTurn, local-first routing, the full safety layer in control_safety.rs) are architecturally cleaner than bolting a local model onto a cloud pipeline — ahead of Cursor/Goose in the control path. The workspace has no dependency cycles, domain-aligned crates, and a small reusable agent SDK with Python/Node FFI bindings. That's a real foundation, not a prototype.

But it is not yet SOTA at deployment scale. Three structural truths hold it back: the sidecar (eri_coreutils) is a monolithic hub importing ~15 domain crates; on-device inference is duplicated and only half-wired (two Ollama paths, LocalProvider not yet in the brain loop); and the build loop is still welded to Claude while control already proved the seam that frees it. None are fatal — all are the "make the good design reach everywhere" kind of work.

The launch gate is not architecture — it's signing. Two independent passes confirmed: the macOS app is codesign --sign - (ad-hoc) with no notarization and no real .dmg. Gatekeeper blocks it on any other Mac. That's the #1 thing between "great codebase" and "a stranger can run it."

Strong candidates (do these)

1 · Lift the build loop onto the ControlTurn seam (a BuildTurn)

Strong

Files: build_agent.rs:216-223, ~510 · mirrors the seam already in control_turn.rs

Problem: control_agent just got a provider-agnostic seam (Claude + local, unit-testable, local-first). build_agent still calls signed_in_client() → post_stream to Claude only — it can't reach on-device models and can't be unit-tested without a cloud login. The request-shaping / streaming / tool-parse code is nearly identical to what control already abstracted. Solution: extract a BuildTurn seam and drive the build loop through a vec of engines, exactly like drive_control_loop. Why first: highest leverage / lowest risk — the pattern is proven this session, the payoff is "eri builds offline" + full test isolation.

2 · Unify the two on-device inference paths + wire LocalProvider into the brain loop

Strong

Files: eri_tab/src/lib.rs (FIM Ollama/llama.cpp) vs eri_inference/providers/local.rs (chat Ollama) · brain_iteration.rs (Local → UnsupportedModel)

Problem: two independent systems manage local models, hitting the same Ollama server with two clients + duplicate download logic, and the general brain loop still rejects ModelChoice::Local. The published roadmap (docs/architecture/local-engine-tier.md) literally lists this as the missing seam. Solution: one LocalInferenceEngine trait both paths share (FIM = a system-prompt specialisation), and make ModelChoice::Local executable in the brain loop. Payoff: the local-first promise becomes real everywhere, not just control.

3 · Break the eri_coreutils dependency star

Strong

Files: eri_coreutils/src/services/mod.rs (30+ handlers), lib.rs (JSON-RPC dispatch) · 15 domain-crate deps · ~14k lines

Problem: the sidecar imports nearly every domain crate (inference, router, apply, tab, index, rules, skills, hooks, mcp, review, codemaps, git, voice…). Every new feature triggers a workspace-wide rebuild; it's a monolith pretending to be a platform — the single largest coupling risk. Solution: a service-loader seam (trait-object handlers that register on load) so heavy services (brain, iterate, mcp) become separate crates. Note: biggest long-term risk, but a bigger lift — start by extracting the 3 heaviest to prove the pattern.

4 · Code signing + notarization + real installer (the launch gate)

Strong · ship-blocker

Files: scripts/build_eri_agent_manager.sh (codesign --sign - ad-hoc), ide/release.sh (checksums only), website/app/download/ → /api/download/macos

Problem: ad-hoc signing + no notarization = Gatekeeper rejects the app on any fresh Mac; nothing real is served at the download endpoint. Not an architecture flaw — a missing pipeline. Solution: Developer-ID sign (--options runtime) → notarytool → stapler → build a .dmg → wire the download route, in CI. Needs your Apple Developer cert.

5 · Harden the loopback control server's token handoff

Strong · security

Files: scripts/eri_control_server.swift:469-495 (token → stdout), :423-436 (bearer check)

Problem: the all-powerful control token is printed to stdout (any process inheriting it, or a writable log, sees it) with no rate-limit / replay guard. Loopback + bearer is good; stdout delivery is the soft spot. Solution: hand the token over a 0600 temp file / UNIX socket instead of stdout; add a simple per-process rate limit. Cheap, closes a local priv-esc path.

Worth exploring (debt, not blockers)

  • execute_tool 9-arg god-function (build_agent.rs:884) → bundle todos/bg/mem into a ToolContext. Worth
  • Shallow Instrumentation/SearchProvider traits (brain_iteration.rs:107-131) → collapse into one CallContext; they exist only to satisfy test stubs. Worth
  • Edit-vs-chat branch duplication (brain_iteration.rs:262-395) → an IntentDispatcher. Worth
  • Domain workflows mixed into eri_inference (20 modules: pr/personas/social/bug_finder…) → feature crates over a pure LLM core. Worth
  • Token metering split across 3 files (proxy.ts/quota.ts/cost_guard.ts) → one accounting service; flag fallback-estimate bills. Worth
  • Stringly-typed Rust↔Swift↔web wire contract → a schema (proto/OpenAPI) + generated stubs + a wire-version header. Speculative
  • Router has no feedback loop — heuristic only; nothing closes wrong-classification / over-escalation back into the thresholds. The eri_graph sink (added this session) is where that loop attaches. Worth

Top recommendation

For shipping: candidate 4 (signing/notarization) is the only thing that turns this from "great repo" into "installable product" — do it the moment you have the Apple cert. For architecture/SOTA: candidate 1 (BuildTurn seam) is the highest-leverage next move — it extends the exact seam we proved this session to the build loop, makes builds local-capable and testable, and is low-risk because the pattern already exists. Then 2 (unify local inference) makes "local-first" true everywhere. Candidate 3 (decouple coreutils) is the biggest long-term win but the largest lift — schedule it once 1+2 land. 5 is a cheap security fix to slot in anytime.

Sequence: 4 (ship) ‖ 1 (BuildTurn) → 2 (unify local) → 5 (token) → 3 (decouple)
