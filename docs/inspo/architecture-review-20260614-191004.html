A · The Remote turn has no recall adapter

Strong

website/lib/agent/run_core.ts · lib/imessage/inbound.ts · crates/eri_cli/src/remote.rs · crates/eri_inference/src/memory/mod.rs

Problem. The recall_memory tool, buildRecallGoal(), and MemoryStore::recall_as_of() are three pieces meant to connect end-to-end — phone asks → command queue → computer searches Tier-B → texts back. But the Remote turn dispatcher (remote.rs:154) runs every goal through run_control_agent — the actuation loop that clicks and types. There is no branch that recognizes a recall goal and runs a pure recall. So a "Search my memory and text me back…" goal is handed to an agent built to do, not to answer; it happens to have recall_hybrid injected as context (control_agent.rs:923) and may improvise an answer, but that's luck, not design.

Two corroborating dead-ends: recall_as_of has no production caller (only the def + tests), and nothing parses the natural-language as_of ("last Tuesday") into a millisecond instant. The bi-temporal "what was true when" capability is fully built at the interface (tool param → goal prose → a tested store method) but the adapter that closes the loop doesn't exist.

Solution. Make kind of Remote turn a real seam. The command-queue payload (or a goal prefix) carries whether this is a Control turn or a Recall turn. remote.rs routes Recall to a small recall adapter: parse the optional time scope → ms, call recall_as_of (or recall_hybrid when no scope), format the hits, return them as the relayed text. The actuation agent stays the Control adapter. Two adapters behind one dispatch = a real seam.

Benefits. The deletion test passes hard: delete the recall adapter and the feature silently degrades to "the actuation agent maybe answers" — which is exactly today's latent bug. Locality: time-parsing + recall ranking + relay formatting live in one place instead of being smeared across a prose goal string and an actuation agent's improvisation. Leverage: a Recall turn is cheap (no control gate, no risky-action confirmation, no HttpBridge) — faster and safer than routing recall through the full control stack. And recall_as_of finally has the caller that justifies its existence.

B · Recall scope+visibility filter duplicated five times

Worth exploring

crates/eri_inference/src/memory/mod.rs — recall, recall_semantic, recall_hybrid, recall_as_of, top_patterns

Problem. Five read methods each open with the same scope+visibility predicate — (o.workspace_hash == hash || o.kind == "fact") && o.is_active() — then diverge only in how they rank. The scope rule ("facts are global, everything else is workspace-scoped") and the visibility rule (active / valid-at) have no single point of control: change either and you grep-edit five sites (mod.rs:352, 441, 472, 492, 531). This is a shallow seam — the duplicated lines are the interface, repeated.

Solution. Extract one candidates(workspace, TemporalScope) -> Vec<&Observation> where TemporalScope is Now (is_active) or AsOf(ms) (is_valid_at). Each ranker consumes the candidate set and only owns its scoring. Note this is orthogonal to candidate A — it deepens the store's read surface regardless of the relay.

Benefits. The scope rule and the bi-temporal visibility rule become testable once, in one place — today they're implicitly re-tested through five rankers. Adding a sixth ranker (e.g. a Letta core-block reader, slice 5) costs a scoring function, not another copy of the filter. Leverage rises; the rankers shrink to what's actually distinct about them.

C · Observation is accreting visibility booleans

Worth exploring

crates/eri_inference/src/memory/mod.rs — Observation, is_active, is_valid_at, supersede_similar_facts

Problem. Three fields now encode "should I show this": superseded: bool, consolidated: bool, valid_to: Option<u64> — plus the implicit kind == "tombstone". superseded is a denormalized shadow of valid_to.is_some() (the slice-4 commit says so). Illegal combinations are representable (superseded=false, valid_to=Some(..)), and the visibility logic is split between is_active and is_valid_at.

⚠ Tension with the live-data decision: superseded is on the wire (synced Tier-B blobs already carry it). A VisibilityState enum is a wire-format change. Surfaced because the smell is real and slice 5 (core/archival tiers) will add another state — better to settle the shape before the third flag, not after.

Solution. Replace the flags with one VisibilityState { Active, Superseded{valid_to}, Consolidated, Tombstone(id) }. is_active() = matches!(Active); is_valid_at() branches on Superseded{valid_to}. A custom serde (de)serialize preserves the existing on-wire superseded/valid_to keys so synced blobs still read — back-compat without the redundant field in the struct.

Benefits. Illegal states become unrepresentable; the slice-5 core/archival tiers slot in as enum variants instead of a fourth boolean. Visibility lives in one match, not two predicates + a free function that mutates two fields in lockstep (supersede_similar_facts:654).

D · valid_from collapsed into ts_ms — model + vocabulary drift

Speculative

CONTEXT.md "Bi-temporal fact" · crates/eri_inference/src/memory/mod.rs Observation

Problem. CONTEXT.md defines a Bi-temporal fact as carrying valid_from / valid_to + learned_at — two timelines (event vs transaction). The slice ships one explicit field (valid_to) and collapses valid_from = learned_at = ts_ms. For v1 that's defensible (no event-time extraction yet), but it means a fact learned today about a past event ("I moved to NYC last year") has valid_from = today — so a true recall_as_of(last_year) would miss it. The capability is "bi-temporal-ready", not bi-temporal; the ubiquitous-language term currently over-promises.

Solution. Either (a) add valid_from: Option<u64> defaulting to ts_ms, so future event-time extraction has a home and is_valid_at reads valid_from..valid_to honestly; or (b) record the v1 simplification in CONTEXT.md + the Observation doc so the vocabulary matches the code. Cheap insurance: do (b) now, (a) when an event-time extractor lands.

Benefits. Keeps the ubiquitous language honest — a future explorer reading "Bi-temporal fact" won't assume an event-start timeline that isn't there. Low urgency: nothing today extracts event-time, so the gap is latent.

Top recommendation

Start with A — the Remote turn recall adapter.

A is the only candidate that's a functional gap rather than hygiene: without it, the recall_memory tool ships but the deep-recall + bi-temporal "what was true when" experience doesn't actually work end-to-end — it degrades to the actuation agent improvising. It also retroactively justifies recall_as_of (today caller-less) and is the natural place the as_of→ms parse lives. B and C are real but safe to defer; B pairs well with slice 5 (a new ranker/tier would otherwise copy the filter a sixth time), and C is best done before slice 5 adds a fourth state. D is a one-line doc fix now, a field later.
