1 · An eri API-call seam under the memory transports

STRONG

Files — crates/eri_inference/src/memory/sync.rs (HttpSyncTransport), against crates/eri_auth/src/eri_auth.rs (AuthClient) and ~12 other ureq call-sites.

Problem — “how to reach the eri API” — build a ureq agent with the right timeouts, resolve the base URL (ERI_API_BASE, default https://eri.dev), attach the Bearer eri_sk_… header, classify ureq::Error::Status into a typed error — is knowledge that now lives in each client. HttpSyncTransport rebuilt it (agent + timeouts + bearer + status match), and it doesn’t even read ERI_API_BASE (the caller must pass a base, so there are now two ways to discover it). Phase 1’s Tier-A profile push needs the exact same plumbing against /api/v1/memory/profile — about to be the third copy.

Deletion test — delete HttpSyncTransport’s agent/base/bearer/error code and the same lines reappear verbatim in the profile transport. Complexity reappears across callers → it was never earning its keep as bespoke code; it wants to be one adapter.

Solution — a small EriApiClient (owns the agent, base-URL resolution, bearer attachment, status→SyncError classification) exposing get(path) / put_json(path, body). SyncTransport stays the domain seam; HttpSyncTransport becomes a ~10-line adapter over EriApiClient targeting /memory/sync, and Phase 1’s HttpProfileTransport is another ~10-line adapter targeting /memory/profile — both over one client.

Benefits — locality: TLS posture, ret/timeout policy, base-URL discovery, and bearer handling change in one place (the security review is auditing exactly these). Leverage: every future eri-API transport is a thin adapter. Test surface: the client’s error-classification is unit-tested once instead of re-proven per transport; the domain seam keeps its StubTransport.

Scope guard: keep this inside eri_inference for now — do not yank the other ~10 ureq sites into it in the same change (that’s candidate 2). Just stop the third copy before it’s written.

2 · Workspace-wide eri-API client consolidation

WORTH EXPLORING

Files — ~12 ureq agent-builders: eri_auth, eri_billing, eri_images, eri_index, eri_inference (providers/*, memory/sync), eri_voice, eri_coreutils.

Problem — the same agent/base/bearer/error pattern is smeared across the workspace; only eri_auth reads ERI_API_BASE, so the others each invent base-URL discovery. This is the full version of candidate 1.

Why not now — it crosses 7 crates and the provider clients (Anthropic/Gemini/OpenAI) talk to provider endpoints, not the eri API, so they don’t all belong behind one client. This is a deliberate, separate refactor — candidate 1 is the wedge that proves the shape first. Echoes the “decouple eri_coreutils hub” item from the landscape review.

3 · What’s already deep — leave it alone

AFFIRM

Recording these so a future review doesn’t “fix” them:

  • merge_observations — pure, total, tombstone-aware; the interface (two vecs in, one converged vec out) is far smaller than the LWW+tombstone logic behind it. Deep. Tested directly.
  • SyncTransport — a real seam (two adapters), carries opaque bytes so crypto + the key never leak across it. The sync() convenience reuses apply_merge rather than re-implementing convergence.
  • profile::distill & profile_contract.ts — pure functions with the bytes/now injected; the interface is the test surface. Textbook.
  • server_encryption.ts — seal/open take the key explicitly (testable w/o env); serverKey() fails fast. Deep + pinned by tests.

Top recommendation

Do candidate 1 now, scoped to eri_inference, as the first act of Phase 1 — extract EriApiClient and reshape HttpSyncTransport into a thin adapter, so the Tier-A profile push lands as a second adapter rather than a third copy. It’s small, it’s local, it keeps the memory seam deep (the plan’s explicit watch-item), and it’s the natural place to apply whatever the security review says about TLS / bearer / base-URL handling — all of which then live in one audited spot. Defer candidate 2; affirm candidate 3.
