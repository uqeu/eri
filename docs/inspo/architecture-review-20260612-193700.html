eri · architecture review · 2026-06-12 · new-feature code

Where this session's features piled up

Scope: the code shipped today — trust layer (action_log.rs + LoggingBridge), proactive (proactive.rs), voice→control (voice_control.rs + the Swift wiring), and the always-on overlay (overlay UI + the NSPanel host + the settings recorder). The Rust additions are clean, tested seams. The friction concentrated on the Swift side, where every new feature attached to one controller.

1 · AgentManagerController has become the everything-object

Strong

Files: scripts/eri_agent_manager.swift — 1319 lines, one class, a 37-case bridge switch

Problem: one controller now owns seven unrelated domains — the WKWebView, voice (startVoiceListening/beginRecognition/teardownAudio), computer-control (startControl/control server/panic-stop), the overlay (buildOverlay/toggleOverlay/resizeOverlay/hotkey), TTS (speak), sidecars, git/workspace, and indexed sources. Each feature I added this session bolted on more state (overlayPanel, speechSynth, voiceControlMode…) and more switch cases. Nothing is independently testable; a change to voice risks the overlay because they share one object's state. Deletion test: deleting the class doesn't move complexity, it scatters it — but it's the wrong kind of "earning its keep": it concentrates unrelated things, which is a god-object, not a deep module.

Solution: extract focused controllers — VoiceController, OverlayController, ControlController — each owning its own state + window/audio, behind a tiny interface (handle(command,payload) or typed methods). The Bridge routes to the right one. Leverage: the overlay can be reasoned about (and unit-tested with a fake bridge) without the voice/audio machinery in scope; locality: voice bugs live in one ~200-line file, not a 1300-line blast radius.

2 · The bridge dispatch is a stringly-typed 37-case switch

Worth exploring

Files: eri_agent_manager.swift handle(command:payload:) · manager.js LOCAL_ONLY + dispatch switch

Problem: every feature adds a case "setVoiceControl" / "toggleOverlay" / "setOverlayHotkey" string on the Swift side AND a matching string on the JS side, by hand, with no shared contract. A typo or a JS/Swift drift fails silently (the command just does nothing). This is the same stringly-typed wire the landscape review flagged, now growing with each feature. Solution: a single source-of-truth command list (a generated or shared enum) and, on the Swift side, a registry where each controller registers the commands it handles instead of one mega-switch. Pairs naturally with Candidate 1 (each extracted controller owns its commands). Locality: a feature's command, handler, and JS caller are defined together, not in three drifting places.

3 · The action log grows unbounded

Worth exploring · correctness

Files: action_log.rs (no cap) · cf. eri_inference/memory/mod.rs cap_observations

Problem: every actuation appends to control-actions.json forever; nothing trims it. Over weeks of use the file (and the undo/history scan) grows without bound — the exact churn the memory store already solved with cap_observations (cap at N, trim oldest, preserve pinned). The trust layer has the same need and no cap. Solution: a cap on ActionLog (e.g. last 500 actions, trim oldest on save), mirroring the memory store. Cheap, and it keeps undo/history fast. Leverage: one place owns "how much history eri keeps," consistent with how it owns memory.

4 · Three parallel turn-seams that haven't met

Speculative

Files: control_turn.rs (ControlTurn), build_turn.rs (BuildTurn), eri_inference/llm_provider.rs (LlmProvider)

Problem: eri now has three "one turn of a model" seams — control (tool-use), build (tool-use), brain (text). They share local-first selection, escalation, and the Ollama transport, but evolved separately (the BuildTurn commit itself noted they're "structurally similar, different return shapes"). Reuse already leaks across them (build_turn imports control's to_local_messages/parse_local_tool_calls). Solution: a shared LocalToolTurn core the control + build adapters both wrap, so escalation/selection/transport live once. Caveat: premature today — the return-shape divergence is real and unifying now risks a leaky abstraction. Revisit once a third tool-using surface appears, or when CandleTransport lands and both want the same in-process path.

Top recommendation

Candidate 1 (split AgentManagerController) is the one that matters. It's the only thing in today's code that got worse with each feature, not better: voice, overlay, control, and TTS all share one 1300-line object's state, so nothing on the Swift side is testable and every change has a wide blast radius. Extracting OverlayController and VoiceController first (the two newest, most self-contained domains) is the highest-leverage, lowest-risk cut, and it sets up Candidate 2 (each controller owns its commands). Candidate 3 is a cheap correctness win to slot in anytime (it's ~15 lines, mirroring a pattern eri already has). Candidate 4 is a note for later, not now.
