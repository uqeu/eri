Lens primer

A module = interface + implementation. Depth = much behavior behind a small interface. The deletion test: delete the module — does complexity vanish (pass-through, shallow) or reappear across N callers (earns its keep)? The interface is the test surface.

Two parallel seams (BuildTurn, ControlTurn) share one wire-translation module (openai_turn.rs). eri-brain is engine #0 in both. build_agent.rs owns MCP loading, Composio session minting, tool dispatch, and system assembly around the build seam.

TOP RECOMMENDATION

Extract one shared EngineTurn core — the two eri-brain adapters are 90% copy-paste

The OpenAI wire is already shared (openai_turn.rs, deep — keep). But EriBrainBuildTurn and EriBrainControlTurn independently re-implement the same HTTP execution: from_env reading the same 3 env vars, new trimming + appending OPENAI_CHAT_PATH, the same post().bearer_auth().send(), the same status/JSON/empty-turn error ladder. Only the final container (Turn vs TurnOutput) differs — exactly the seam the module doc claims is centralized but isn't. Same duplication for the select_*_turn_with ordering and the Local*Turn pair.

Deletion test: the wire module passes today (delete it → both adapters re-grow JSON-shape knowledge). But the executor duplication fails the test in the other direction: a fix to one (timeout, retry, auth-header rename, streaming) must be hand-mirrored to the other or they drift. Centralizing the HTTP call deepens the seam the docs already promise.

C2 · composio_session + ${COMPOSIO_MCP_URL} indirection earns its keep — but session lifecycle is leaky

composio_session.rs:45 · build_agent.rs:2076 (mcp_vars_with_session) · eri_mcp/config.rs:245 (builtin)

Verdict on the var-indirection: it earns its keep. The single ${COMPOSIO_MCP_URL} placeholder + fail-closed expand_vars means a minted session, a cloud-relayed session, or "skip composio entirely" are all one config path with one code path — delete it and the mint/relay/skip branches reappear in load_mcp. Fail-closed is correct: parse_session_url → None → var unset → server skipped (config.rs:255). Good.

Problem (lifecycle): the session is minted fresh on every depth-0 run (mcp_vars_with_session POSTs a new trs_… each launch unless the env var is pre-set). No reuse, no TTL awareness, no expiry handling: a long build whose session expires mid-run gets opaque per-tool failures ("that step couldn't be completed") with no re-mint. See stress risk S1.

BEFORE
// every run: new session, no cache, no expiry path
mcp_vars_with_session() {
  if env COMPOSIO_MCP_URL set -> use it
  else mint via POST (new trs_ each time)
}
AFTER (deepening)
// session as a small typed value w/ minted_at;
// cache on disk under .eri, reuse until ~TTL,
// re-mint on 401/expired tool error mid-run.
struct ToolRouterSession{ url:String, minted_at:Instant }
WORTH EXPLORING

C3 · intent.rs is a clean seam — but the keyword pile has real misroutes

intent.rs:62 (classify_intent) · eri_cli.rs:998 (dispatch_external)

Verdict on the seam: the &str → Intent signature is genuinely deep + correct as an upgrade seam — dispatch only knows Intent, the eri-brain classifier can swap the body with no call-site change (the doc's stated contract holds). Keep the seam.

Problem (the body): ordered keyword heuristics over-fire. Concrete misroutes the tests don't cover:

  • "delete all my files" / "close my bank account" → no control/build verb, no connector → Answer (tool-capable). A destructive imperative lands in the path that has connector tools. (See S2 — this is the highest-stakes misroute.)
  • "add a meeting tomorrow" → add is a Build verb; meeting isn't in ARTIFACTS → falls through; but "add a calendar event" hits Build's add+? no artifact → Answer, while "create an event" → create is Build verb, event not artifact → Answer. Fragile, order-dependent.
  • "open Spotify" (no second action word) → APP_VERBS has open → Control ✓, but "play despacito" → play ✓ Control; "summarize my slack" deliberately stays Answer (good) — yet "search my slack" hits the APP_NAMES+search rule → Control, not Answer.

Deepening: keep the seam; make the fallback safer (route ambiguous-but-imperative to a confirm rather than silently to Answer), and add a thin "destructive verb" guard that biases to Control's gated path (which has the confirm/denylist) rather than the ungated Answer path.

Deletion test: mixed. The loop (drive_build_loop) earns its keep. Deepening (low-risk, mechanical): lift cohesive groups behind small interfaces — mcp.rs (load_mcp / mcp_vars / call_mcp_tool / mcp_tool_specs), tools/exec.rs (the execute_tool match + fs/git/bash), system.rs (build_system + brand wiring). Each is a deeper module: the loop calls execute_tool(...) and load_mcp(...) without seeing 1,600 lines. No behavior change; pure relocation behind existing call shapes.

STRONG

C5 · Two escalation policies for one concept — unify the engine-ladder driver

build_agent.rs:508-553 (per-turn retry from engine[0]) · control_agent.rs:1165-1188 (sticky engine_idx)

Problem: the build loop re-tries engines from index 0 every turn (so after a transient eri-brain failure it goes back to eri-brain next turn). The control loop uses a sticky engine_idx — once escalated to Claude it never returns to eri-brain for the rest of the run. Same domain concept ("escalate engines for one turn / one goal"), two divergent hand-rolled policies. This is a silent behavioral fork: the cost/latency profile of a build vs a control run differs for reasons no one chose.

BEFORE — build: retry from 0 each turn
for (i,engine) in engines.iter().enumerate(){
  match engine.run(..).await { Ok=>break,
    Hard(e)=> if i+1<len {continue} else {return Err}}}
// next turn: starts again at engines[0]
BEFORE — control: sticky idx
let turn = engines[engine_idx];
match turn.run(..).await { Err=> {
  if idx+1<len { engine_idx+=1; continue }
  return Err } }
// once escalated, stays escalated

Deepening: one EngineLadder (or a shared function) with an explicit, documented policy (sticky vs per-turn) chosen on purpose and shared by both loops. Then a future "remember eri-brain just failed, skip it this run" decision lives in one place — and the falling-Claude-share metric the learning loop depends on is measured consistently across surfaces.

Correctness / stress risks

  • HIGH S2 · destructive prompt → ungated Answer path. classify_intent sends "delete all my files", "wipe my downloads" (no control/build verb, no connector keyword) to Answer (agent::ask), which carries connector + (potentially) MCP tools and is not behind the control confirm/denylist gate. The safe default ("ambiguous → Answer") is unsafe for destructive imperatives. intent.rs:103, eri_cli.rs:1025. Mitigation: a destructive-verb guard that routes to the gated Control path.
  • MED S1 · Tool Router session expiry mid-run. Session minted once per run, no TTL/re-mint. If Composio expires trs_… during a long loop, every meta-tool call returns the neutral failure with no recovery; the model may loop retrying. composio_session.rs, build_agent.rs:2076.
  • MED S3 · eri-brain tool-call id collision risk. parse_openai_tool_call synthesizes eri-brain-{i} when a server omits ids (openai_turn.rs:229); parse_local_tool_calls uses local-{i}. In the control loop these ids are not threaded back as tool_call_id (control results are role-based), so it's latent there; but in the build loop the eri-brain path round-trips ids through to_openai_messages — a server that emits duplicate/empty ids across turns could mis-pair tool_results. Add a uniqueness/sequence guard.
  • MED S4 · empty-turn → escalate can mask a working-but-terse engine. Both eri-brain adapters treat "no text and no tool calls" as Hard/escalate (build_turn.rs:382, control_turn.rs:545). A model that legitimately answers with an empty string + stop_reason:end_turn (e.g. an acknowledged no-op) is forced to escalate to Claude — burning tokens and inflating Claude-share, the exact metric the moat is measured by.
  • LOW S5 · build eri-brain ignores stop_reason from the wire. eri_brain_turn derives stop_reason purely from "did it call tools" (build_turn.rs:411), discarding any real finish_reason/length the server sent — so a truncated eri-brain build turn is reported as a clean end_turn, unlike the Claude path which narrates max_tokens (build_agent.rs:567).
  • LOW S6 · strip_json_comments ignores strings-with-//. Documented as "naive, doesn't track markers inside strings" (config.rs:330). A URL like "https://x" inside a value is fine (it's in-string and skipped), but a /* */ sequence inside a string value would be mangled. Edge-case, low likelihood for mcp.json shapes — noted, not blocking.
  • OK No unwrap/panic landmines in the new code. chosen.expect(...) (build_agent.rs:552) is justified by the loop invariant; create_tool_router_session and the wire parsers are exhaustively Option/Result with fail-closed defaults. Secret hygiene is good (api_key never logged; bearer via bearer_auth; is_secret_env strips ERI_*/provider keys before bash).

Speculative

SPECULATIVESP1 · fold BuildTurn + ControlTurn into one EngineTurn<Out>

The two traits differ only in output type (Turn vs TurnOutput) and one error enum. A generic trait EngineTurn{type Out; async fn run(...)->Result<Self::Out,EngineError>} plus the shared executor (C1) would make eri-brain/local/Claude literally one set of adapters. High blast radius, defer until C1+C5 land and prove the shapes converge.
