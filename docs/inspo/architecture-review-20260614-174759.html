Architecture Review · deepening opportunities

Account, identity & two-product billing

One WorkOS organization should be the single account that carries both products: cameras (manual, invoiced — organizations.camera_limit) and the developer API (Stripe — org_credits). Today entitlement is resolved two different ways and app access is gated by a live Stripe call. This review maps the friction and the deepenings that get it to industry grade.

Candidate 1

One deep Account module, keyed by the WorkOS org

Strong

Files

  • hs_app/lib/developer-api.ts (resolveOrg — already deep)
  • hs_app/lib/auth/workos.ts (organizationId, role)
  • hs_app/app/api/auth/check-access/route.ts
  • hs_app/app/api/subscription/camera-limit/route.ts
  • hs_app/app/api/camera-names · /api/org/*

Problem

"Which account is this?" is answered in two incompatible ways: the camera side keys on user_email (→ subscriptions), the API side keys on org_id (→ resolveOrg → org_credits). A single email could map to several orgs on the API but exactly one Stripe subscription. Org-resolution logic is duplicated; the camera app never touches organizations at all.

Solution

Promote the existing deep resolveOrg into a shared Account module: resolveAccount(session) → { orgId, role, cameraLimit, region }, resolved from WorkOS organizationId via organizations.workos_org_id (auto-provision on first authenticated request, mirroring resolveOrg's race-safe upsert). Every caller — access gate, camera-limit, camera-add, developer/* — goes through this one seam.

Benefits — locality & leverage

  • leverage: one call answers "who is this account, what can it do" for both products.
  • locality: org-resolution + entitlement live in one module; the WorkOS→org mapping is changed in one place.
  • tests: the interface becomes the test surface — a FakeAccountStore lets every route be tested without Supabase or Stripe.
Before — shallow, duplicated
check-access → Stripe
camera-limit → subscriptions
developer/* → resolveOrg
3 ways to ask "who?"
After — one deep seam
* → resolveAccount()
↳ orgId, role
↳ cameraLimit (manual)
↳ credits (Stripe)
Deletion test

Delete the Account module → org-resolution + entitlement logic reappears across ~6 routes (it already does today). Complexity concentrates, not vanishes → it earns its keep. This is a genuinely deep module.

Candidate 2

Camera entitlement: one source, per-org count, enforced at the add seam

Strong

Files

  • hs_app/app/api/subscription/camera-limit/route.ts
  • hs_app/app/api/connector/cameras · /api/agent/[id]/cameras (the real add seam)
  • migration: organizations.camera_limit

Problem

The limit module is shallow and bypassed. It reads subscriptions.camera_limit (wrong source), counts agent_cameras globally (.eq('streaming_enabled',true) with no org filter — one camera anywhere blocks everyone), trusts ?email= with no auth, and is never called on the add path — it's advisory UI only.

Solution

A deep assertCanAddCamera(orgId) that reads organizations.camera_limit, counts agent_cameras WHERE org_id = $1, and runs inside the camera-create transaction — the real seam, not the UI. Over-limit throws a typed CameraLimitError (→ 409). Same authorize-then-act discipline as the API's reserve/settle.

Before
UI calls camera-limit
count(*) all cameras
add-camera route:
insert — no check
After
add-camera route:
assertCanAddCamera(org)
count WHERE org_id
then insert

Benefits

  • locality: the rule "an account caps at N cameras" lives at the one place a camera is born — impossible to bypass.
  • tests: one test ("11th camera on a 10-cap org → 409") covers it; today it's untestable because the check isn't wired in.
  • kills both live bugs (global count, unauth email) by construction.
Candidate 3

Slim the Stripe webhook to one job: ARK credits

Strong

Files

  • hs_app/app/api/webhook/stripe/route.ts (~540 lines)
  • + the camera Stripe checkout/portal/trial routes

Problem

One file carries two unrelated jobs. Keep: checkout.session.completed → handleCreditPackPurchase (gated on ark_credits metadata), refunds, disputes — the API credit path. Remove (per decision): customer.subscription.*, invoice.*, and the mode==='subscription' branch that syncs subscriptions.camera_limit. Cameras are invoiced manually now.

Solution

Delete the camera-subscription handlers + syncSubscriptionToSupabase/handlePaymentSucceeded, and the camera checkout/portal/trial routes. The webhook collapses to a single responsibility with a tiny interface: "a paid credit-pack session grants credits to an org." The split is already clean — ark_credits is checked first (line 400), so removal touches zero credit lines.

Before — 17 event cases
checkout.* (credits)
charge.refund/dispute (credits)
customer.subscription.* ×6
invoice.* ×6
payment_intent.* / customer.*
After — one job
checkout.session.completed
charge.refunded
charge.dispute.*
→ grant / revoke credits

Benefits

  • deletion test (inverse): removing the camera half shrinks the interface to one verb — the remainder is unambiguously a "credits" module.
  • locality: no future reader wonders whether a subscription event still moves a camera limit.
  • removes a whole class of Stripe state (subscription lifecycle) you no longer reason about.
Revenue-safety note

The developer-API Stripe path (checkout → grant_credits, refund/dispute → revoke_credits) is fully preserved. This candidate only removes the camera-subscription billing you've decided to drop.

Candidate 4

Access gate = org membership, not a live Stripe call

Worth exploring

Files

  • hs_app/app/api/auth/check-access/route.ts
  • hs_app/lib/hooks/useAccessControl.ts
  • hs_app/middleware.ts

Problem

App access is decided by isAdmin || hasActiveStripeSubscription, where the second term is a synchronous Stripe API call with a 10s timeout on the dashboard hot path. When Stripe is slow the UI must retry with backoff; the gate depends on an external vendor for every session. With manual invoicing there's no subscription to check anyway.

Solution

Access = "the WorkOS user resolves to an org" (invite-only already enforces who can authenticate). Gate becomes a single resolveAccount() lookup (Candidate 1) — local, fast, no Stripe. Camera capacity (limit 0 vs N) is separate from access. Admins stay via role/allowlist.

Latency & failure mode
BeforeStripe call · ≤10s · vendor-dependent
After1 indexed row read · <20ms · local

Removes the only third-party dependency from the login hot path and the whole "entitlement check unavailable / retry" UI branch.

Benefits

  • leverage: access + entitlement answered by the same module.
  • tests: "user with no org → denied; user in org → allowed" is a pure unit test, no Stripe mock.
Candidate 5

Make RLS the enforcement seam, not per-route key choice

Worth exploring

Files

  • hs_app/lib/supabase.ts (anon vs service-role)
  • 13+ routes using service-role + in-code membership checks
  • Supabase RLS policies (not in repo — audit needed)

Problem

Tenant isolation is enforced in application code: most routes use the service-role client (RLS bypassed) and re-check org membership by hand. The anon-client routes (camera-names, camera-limit) assume RLS policies exist — none are in the repo. Today's 401 incident showed how fragile the key path is. A forgotten in-code check or a misconfigured policy fails open.

Solution

Codify org-scoped RLS policies as migrations (the seam), so isolation holds even if a route forgets a check or a key leaks. Reserve service-role for genuine cross-tenant work (webhooks). Add policy tests. Document the rule in CONTEXT.md.

Before — isolation in code
service-role (RLS off)
+ if(member) check ×13
miss one → leak
After — isolation in DB
RLS policy: org_id ∈ my orgs
routes inherit it
fail closed by default

Bigger change; sequence it after the account unification so policies target a single org seam.

Candidate 6

Retire the legacy customers table into organizations

Speculative

Files / tables

  • customers (max_cameras, api_key, organization)
  • honour_agent_settings.customer_id → org_id
  • agents.customer_id / agent_cameras.customer_id

Problem

Three account-ish entities coexist: customers (legacy sales record, has an unused max_cameras=5), subscriptions (Stripe), organizations (WorkOS). Cameras carry both customer_id and org_id. This dual identity is a standing source of "which id do I use here?" friction.

Solution

Once Account (C1) is the single seam, migrate Genetec settings + agent/camera links onto org_id and drop customer_id + the customers/subscriptions tables (or freeze them read-only as history).

Deletion test

Delete customers → max_cameras becomes organizations.camera_limit (C2), Genetec creds move to org. Complexity concentrates onto one entity → worth doing, but only after C1/C2 land. Do not start here.

Top recommendation

Start with Candidate 1 — the Account module — then 2 → 3 → 4.

Everything else hangs off "which account is this?". The API side already has the deep, race-safe answer (resolveOrg); promoting it to a shared Account seam keyed by the WorkOS org is the smallest change that makes the camera side correct and unifies both products onto one entity. With that seam in place: camera_limit enforcement (C2) becomes a one-liner at the add path, the webhook slim-down (C3) is pure deletion, and the access gate (C4) drops its Stripe dependency for free.

Suggested build order
1 · Account seam → 2 · camera_limit at add → 3 · slim webhook → 4 · org-based access → 5 · RLS seam → 6 · retire customers

Each step is TDD-able through the Account interface with a FakeAccountStore — no Supabase or Stripe needed to test entitlement logic. Decisions to record as ADR-0004: WorkOS org = the account; camera_limit is manual/invoiced; API credits stay Stripe; limit is per-org.
