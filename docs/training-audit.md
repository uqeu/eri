# Training Pipeline Audit — eri-brain vs the 80-paper corpus

**Date:** 2026-06-17
**Scope:** `training/` (corpus builder, manifest, validator, generator, MLX + CUDA finetune scripts) audited against `docs/papers-synthesis.md` and the training-relevant primary papers (KTO `paper_15_kto`, DPO `2305.18290`, When2Call `2504.18851`, S-LoRA `2311.03285`, CIPHER `21194_Aligning`).
**Mandate:** the founder will not spend on an AWS finetune until the approach is confirmed SOTA-correct. The pipeline predates these papers. This is an audit — **no code was changed.**

---

## TL;DR verdict

**DEFER the AWS finetune.** The pipeline is well-engineered and provenance-clean, but it is solving the **wrong problem for eri's current stage** (pre-launch, zero users, zero behavioral data) and its **training objective is incomplete in a way the papers say will actively hurt the one feature it most wants (tool-use restraint).**

- The **provenance discipline is genuinely excellent** and is the single biggest thing it got right — better than most production shops.
- But the corpus would produce a **generic open-SFT Qwen with an eri persona skin**. The synthesis is unambiguous that production assistants (ChatGPT/Claude/Gemini) deliver personalization through **profile + memory + RAG, not per-user fine-tuning** — and eri *already shipped* that runtime memory brain. A base-model SFT does not move eri's moat right now.
- The objective is **SFT-only**. For tool-use restraint specifically, When2Call (`2504.18851`) shows SFT alone either under-corrects or makes the model **too conservative (−6.2% BFCL)** — you need a **preference objective (RPO/KTO/DPO)** to get restraint cleanly. eri ships restraint *data* but trains it with the *wrong objective*.
- KTO — the objective eri's own ADR-0004 and personalization doc declare "binding" — **is not implemented anywhere**. There is no preference-optimization code path at all.

**Recommendation:** do **not** burn AWS GPU-hours on the base SFT now. Instead (a) ship the runtime memory/RAG brain that the synthesis ranks P1–P8 (0 training, 0 cloud tokens, compounding), (b) start logging the binary kept/edited/rejected signal *the day eri ships* so a KTO loop is *possible later*, and (c) when there is data, run **KTO (not SFT) on the eri-specific slice**, served via S-LoRA. The SFT corpus tooling is not wasted — it becomes the cold-start/SFT-warmup base for that KTO run. Just don't pay for the bake-off + 32B finetune before there is a single user.

## 1. What the pipeline got RIGHT

1. **Provenance is load-bearing and done correctly.** This is the standout. `validate.py` enforces a hard gate: every generated record must carry `meta.provenance == "open-model"`; `datasets.yaml` carries an explicit `OFF_LIMITS` list (APIGen-MT-5k, ToolBench, UltraChat, OpenHermes-2.5, Orca, Capybara, No-Robots, WildChat asst turns, ShareGPT, Alpaca, Vicuna, WizardLM, SlimOrca, lmsys asst turns); and `generate_eri_data.py` has a **hard host-fragment guard** that refuses any `anthropic`/`openai` base URL. The 2026-06-15 audit even dropped Glaive-FC, Hermes-FC, Tulu-3-mixture, and ToolACE when their GPT/Claude taint or disputed provenance was identified, and replaced them with Nemotron-Agentic + Magpie + the DeepSeek-R1 reasoning axis. **This is exactly the discipline the papers and the binding ADR demand, and it is rare to see done this thoroughly.**
2. **No-teacher generation is correct by construction.** eri-specific data is generated by open models (Kimi K2.7 / local Qwen2.5-72B / DeepSeek-R1), never Claude/GPT, never eri's own CLI traces. Claude only orchestrates. The Claude-authored `seeds/` are walled off as structural scaffolding (`seed-template` provenance) and provably never enter the corpus (separate provenance tag, validator rejects them from `eri_data`).
3. **The "invisibility" lint is a real product-correctness check**, not just hygiene: the assistant's natural-language content may never name a tool/Composio/MCP, while structured `tool_calls` are exempt. This directly enforces the "one eri voice out" identity mandate.
4. **Restraint data IS in the corpus.** The actual `mlx_data/train.jsonl` contains ~1,710 xlam-irrelevance-style and ~1,721 When2Call-style canned no-call replies — the tool-restraint signal the synthesis flags as cutting wrong calls 60–83% is physically present.
5. **Engineering quality is high.** Stdlib-only green gate (validator + dry-runs run with no GPU/network/key), deterministic dedup by normalized-message SHA-256, per-dataset try/except so one bad set never kills a run, a quality selector (pool→score→diversify→top-N) rather than first-N, and genuine self-tests on every module. Two backends (MLX for Apple Silicon, CUDA PEFT+TRL) train the same corpus.
6. **Base-model + serving choice is defensible.** Dense **Qwen3-32B (Apache-2.0)** is chosen explicitly (ADR-0004) over the Qwen3-30B-A3B MoE for **mature vLLM multi-LoRA + stronger tool-calling (BFCL-v3 ~75.7)**, and over Qwen3.5-35B-A3B whose LoRA is "currently broken in vLLM." The serving plan is **vLLM multi-LoRA** — which is exactly the S-LoRA pattern (see §4). This reasoning is sound and matches the LoRA-maturity evidence.

## 2. What's WRONG / outdated vs the papers (ranked by severity)

### CRITICAL-1 — Objective is SFT-only; the papers say that is insufficient for restraint, and KTO (the "binding" objective) is unimplemented
The pipeline trains **SFT only** (`lora_finetune.py` uses TRL `SFTTrainer`; `mlx_finetune.py` calls `mlx_lm.lora` plain SFT). There is **no DPO, no KTO, no RPO code anywhere.** Yet:
- ADR-0004 §5 and `personalization-learning-loop.md` both declare **"Objective: KTO"** as *binding*. The code does not honor the architecture decision.
- **When2Call (`2504.18851`) is explicit that SFT alone fails for the restraint behavior** eri most wants. Adding negative/restraint examples to the SFT blend made the model **"too conservative," a −6.2% drop on BFCL Live AST (4B)**; "this issue is compounded if SFT is followed by a helpfulness step." Their fix is **RPO (preference optimization) with a low KL-penalty of 0.05** and a **2:1 tool:non-tool** SFT blend, which drove **tool-hallucination 19% → 1.2% (8B)** while *preserving* BFCL (RPO 62.5% vs SFT 57.5% AST). The headline "60–83%" in eri's docs is a *derived* relative reduction, not a paper quote — the paper's own number is **19%→1.2%** and the RPO-vs-baseline reduction is closer to ~88–94%. Either way: **SFT-only restraint data, with no preference objective, will at best under-correct and at worst make eri annoyingly conservative.**
- The README claims "start with SFT … the self-improvement loop later adds KTO." That sequencing is *fine in principle* — but it means the **current corpus + scripts cannot produce eri's stated differentiator** (restraint + per-user adaptation) on their own. Paying for the SFT run now buys a generic instruct model.
- **Bonus finding that further weakens the "SFT-first" case:** the KTO deck shows **KTO can skip the SFT stage entirely at 13B/30B scale** ("KTO is the only [method] that consistently shows this behavior"; DPO-without-SFT rambles/hallucinates). Qwen3-32B is already a strong instruct base. So the assumption that an expensive SFT warm-up *must* precede KTO is not even necessarily true at eri's model size — another reason the SFT-now spend is questionable.

**β / hyperparameter readiness (the synthesis's specific ask):** because no preference objective exists, **there is no β to be right or wrong** — the risk is latent, not yet committed. When the KTO/DPO path is built, honor the guidance, with one correction to the source attribution:
- **DPO's own paper (`2305.18290`) uses β = 0.1 by default** (0.5 for summarization). The "β = 0.01–0.02, never 0.1" guidance is **not from the DPO paper** — it comes from the *Reference-Policy* follow-up (`naacl.447`) which finds the DPO default of 0.1 is *too high* for preference fidelity. So the synthesis's "never 0.1" is correct *advice* but is a critique of DPO's default, not DPO's own recommendation. Use **β ≈ 0.01–0.02 for DPO**.
- **The KTO β ≈ 0.05–0.10 number cannot be sourced from our corpus.** The `paper_15_kto.pdf` in `papers/` is a **slide deck**, not the original Ethayarajh et al. manuscript, and it gives **no recommended β number** — β is described only qualitatively as risk/saturation sensitivity. The 0.05–0.10 figure must be sourced from the original KTO paper before it is committed to config. What the deck *does* confirm: **λ_D = λ_U for balanced data**, the imbalance rule `λ_D·n_D / (λ_U·n_U) ∈ [1, 1.5]`, and "gain sensitivity > loss sensitivity."
- When2Call's restraint **KL-penalty = 0.05** (this is the RPO low-KL value, exact from the paper).

### CRITICAL-2 — Fine-tuning a base model is the wrong PRIORITY right now (premature; no usage data)
This is the BIG question, answered bluntly: **fine-tuning a base model is premature.**
- The synthesis is unambiguous (lines 12, 164–173, and the whole §2 ranking): **"LoRA serving and most fine-tuning are deferrable until there's user data."** Production assistants do **profile + memory + RAG, not per-user fine-tuning** (`2501.13121` Episodic Bench: paragraph-level RAG beats fine-tuning for multi-event recall; LaMP `2304.11406`: retrieve-and-inject profile, don't dump; CIPHER `21194`: personalize a *frozen* LLM via retrieved inferred preferences, **no fine-tuning**, 31–73% fewer edits).
- **eri already shipped the runtime brain** these papers point to: `eri_inference::memory` (bi-temporal `recall_as_of`, hybrid `0.55·sem+0.30·lex+0.15·rec`, MMR diversity, `consolidation.rs`), heuristic style profile, `remote_recall`. That is where eri's personalization lives *today*, at **0 cloud tokens** and **0 training**.
- The synthesis's top eight build items (P1 scoring math, P2 surprise-gated writes, P3 CIPHER style, P4 When2Call decision head as a *prompt*, P5 RRF+rerank, P6 profile consolidation, P7 trained router, P8 reflexion) are **all cheap, mostly 0-token, and need no GPU spend** — and they compound. Per-user LoRA is **P9**, explicitly "deferred until private testing yields signal."
- A base SFT now cannot be personalized per-user (that needs the KTO loop + data), cannot be evaluated against eri's own tasks (no users, no task distribution), and would have to be **re-run** once the real objective + data exist. **It is GPU spend that buys a throwaway artifact.**

### HIGH-3 — The eri-authored "restraint" category is mislabeled vs the paper's definition
eri's *generated* `restraint.jsonl` is general-knowledge Q&A ("Who wrote The Great Gatsby?" → "F. Scott Fitzgerald.") — i.e. **"answer directly from knowledge"**, which is only *one* of When2Call's four behaviors. The actual tool-restraint signal (decline to call an *irrelevant available tool*, or ask a follow-up when a required param is missing) comes entirely from the **open When2Call/xlam-irrelevance** datasets, not from eri's own slice. That's acceptable (the open data carries it) but means eri's authored restraint examples are **not exercising the hard decision** (tool-available-but-shouldn't-call) and the taxonomy is **4-way** (direct / tool-call / follow-up / unable), not the 5-way the docs imply ("unable" = "cannot answer", one category).

### HIGH-4 — Internal contradiction: docs ban "permissive teachers," manifest is full of them
`personalization-learning-loop.md` and the README both state the rule **"not even a permissive teacher (DeepSeek-R1/Qwen)"** for distillation. But `datasets.yaml` deliberately includes **Magpie (self-synthesized by Qwen2.5-72B), Mixture-of-Thoughts (DeepSeek-R1 reasoning traces), Nemotron-Agentic/Post (NVIDIA open models)** — all open-*model*-generated public datasets. This is **defensible and almost certainly fine** (using a *published, permissively-licensed* open-model dataset ≠ running a teacher yourself to distill for this purpose — the manifest comment makes that distinction explicitly). **But the prose rule and the manifest read as contradictory**, and a careless reader (or a future auditor, or opposing counsel) could see Mixture-of-Thoughts as "DeepSeek-R1 distillation." **Fix the wording**, not the data: state clearly that *consuming a public open-model-authored dataset is permitted; running an open model yourself to generate distillation pairs for this corpus is not.* Note `generate_eri_data.py` does the latter (open model generates eri's slice) — which the README explicitly blesses, so the rule as written ("not even a permissive teacher") is *already violated by eri's own generator* unless you read "teacher" narrowly as "frontier/Claude/GPT." This needs one clear sentence to resolve.

### MEDIUM-5 — README dataset table is stale / contradicts the live manifest
`training/README.md` §"Dataset mix" still lists **glaiveai/glaive-function-calling-v2, ToolACE, hermes-function-calling-v1, allenai/tulu-3** as the tool/chat sources — exactly the four sets the 2026-06-15 audit moved to `OFF_LIMITS`. The personalization doc §"Commercial-safe dataset mix" has the same stale list (Glaive-FC + ToolACE + Hermes-FC). The *manifest and validator are correct*; the *documentation lies*. Anyone reading the docs to sanity-check provenance would conclude tainted sets are in the mix. Pure doc-rot, but it undermines the provenance story it is trying to tell.

### MEDIUM-6 — `lora_finetune.py` real-training corpus loader is a stub
`_build_corpus()` (CUDA path) loads each manifest dataset with a bare `load_dataset(d["hf_id"], split="train")` and **no per-dataset column→messages mapping** (the comment admits "per-dataset column mapping … applied here in the real run"). It also ignores `split`/`config` from the manifest (When2Call has no `train` split; Mixture-of-Thoughts needs `config: all`) and the `tulu_allowed_sources` filter in `config.yaml` references Tulu, which is now OFF_LIMITS. So the **CUDA path would crash or train on raw, unconverted rows** on a real run. Only the **MLX path (`prepare_corpus.py`) actually converts** datasets to the messages schema. The AWS finetune (CUDA/GPU) would run the *broken* path. **This alone is a reason not to launch the AWS run as-is.**

### LOW-7 — Corpus scale + balance
~3.7k eri-specific records + ~19k open-blend = ~22.8k in `mlx_data`. For a 32B LoRA SFT this is on the small side but workable for a persona/format pass. The eri slice is balanced (meta_tools 962 / persona 972 / restraint 920 / routing 920). No train/test leakage check beyond exact-dedup (no near-dup across the train/valid split boundary other than the SHA dedup — fine for SFT, would matter for eval).

### LOW-8 — `config.yaml` LoRA params are reasonable but untuned for the objective
r=16, α=32 (scale 2.0), dropout 0.05, lr 2e-4, cosine, 3 epochs, all 7 Qwen projections targeted. Fine for SFT. When KTO is added, lr should drop (preference optimization typically 5e-7–1e-6, cf. When2Call's 7e-7–9e-7 for RPO) and epochs ≤ 1–2.

## 3. Recommendation

**DEFER the AWS finetune. Do not spend now.** Ranked actions:

**A. Do NOT run the base SFT on AWS yet.** It produces a generic instruct-Qwen with an eri persona, cannot be personalized, cannot be evaluated (no users), trains restraint with the objective the papers say is insufficient, and the CUDA path is a stub that would crash or train on garbage (MEDIUM-6). The artifact would be thrown away once the real KTO loop + data exist.

**B. Ship the runtime brain first (0 GPU, 0 training, compounding).** Execute synthesis P1–P8: the three missing scoring terms (importance + Ebbinghaus strength-decay + competitive winner), surprise-gated writes, CIPHER edit-learned style (replaces the heuristic facet, **no fine-tuning**), the When2Call decision head **as a prompt-only 4-way classifier** in front of the Composio router (Phase A needs no training and captures most of the restraint win), RRF + cross-encoder rerank, async profile consolidation. These are where eri's personalization moat actually lives today and they cost ~0 cloud tokens.

**C. Start logging the KTO signal the day eri ships.** Per `personalization-learning-loop.md`: record per assistant turn the prompt, response, engine, and outcome (kept / edited+diff / rejected / 👍👎). KTO needs *binary* signal and eri *already produces it* (continued vs re-asked/edited) — but only if it is captured from day one. **This is the prerequisite that unblocks the entire fine-tuning future and costs nothing but a schema + a write.**

**D. When (and only when) there is data, train KTO — not SFT — served via S-LoRA.** SFT-warm the base on the existing clean corpus *once* (the current tooling is the right tool for *that* step), then run **KTO** on the per-user/cohort signal with **β ≈ 0.05–0.10** (never 0.1), λ_D=λ_U=1, lr ~7e-7. Serve adapters with vLLM multi-LoRA (the S-LoRA pattern: never-merge, `xAB` on-the-fly, unified paging — 2,000+ adapters, ~4× throughput on one warm GPU). The base/serving choice (Qwen3-32B dense) is already correct.

**E. Fixes to make regardless (cheap, do before any future run):**
- Fix the broken CUDA `_build_corpus()` to use the same converters as `prepare_corpus.py` and honor manifest `split`/`config`; drop the dead `tulu_allowed_sources` config (MEDIUM-6).
- Update `training/README.md` and `personalization-learning-loop.md` dataset tables to the *actual* manifest (remove Glaive/ToolACE/Hermes/Tulu) (MEDIUM-5).
- Resolve the "no permissive teacher" wording vs the manifest + generator (HIGH-4) with one clear sentence.
- Relabel/augment eri's `restraint` category to include true tool-available-but-decline and missing-param-follow-up cases (HIGH-3).

### The honest tradeoff
**Deferring costs eri nothing real right now and saves a wasted bake-off + 32B GPU-month pre-revenue.** The only thing a finetune-now buys is a *demo-able* "we have our own model" artifact — but it would be a generic one, indistinguishable from base Qwen3-32B + a good system prompt, and the synthesis says a good system prompt + the shipped memory brain already deliver that. The moat (per-user adaptation, falling Claude-escalation share) is **unreachable without usage data no matter how much you spend today.** Spend the GPU budget the day you have the binary signal logged and a KTO path built — not before.

## Appendix — primary-paper facts grounding this audit

- **When2Call `2504.18851`** (NVIDIA): objective **RPO** (not DPO/SFT), KL-penalty **0.05**, SFT blend **2:1 tool:non-tool**, RPO preference set 1:1. **4-way** taxonomy (direct / tool-call / follow-up / unable). SFT-only → too conservative, **−6.2% BFCL AST (4B)**; RPO → **tool-hallucination 19%→1.2% (8B)** while raising BFCL AST 57.5%→62.5%. **Central claim: a preference objective, not SFT, is what gets restraint without sacrificing legitimate tool-calling.** ("60–83%" in eri docs is a derived figure, not a paper quote.)
- **S-LoRA `2311.03285`** (MLSys 2024): keeps adapters **separate**, computes `xAB` on-the-fly (merging is inefficient for multi-LoRA serving), **unified paging** for KV+adapters, serves **2,000** adapters on one base, **up to 4× vLLM-packed / 30× PEFT** throughput. Per-user multi-LoRA serving infra is **demonstrated and open-source** — the *serving* cost barrier is solved (the learning side is not its scope). Validates eri's vLLM-multi-LoRA serving plan.
- **CIPHER / PRELUDE `21194`** (NeurIPS 2024): personalizes a **frozen** LLM with **no fine-tuning** — retrieve top-k inferred preference strings by cosine, inject into prompt; learn from user **edits** (Levenshtein token cost > δ triggers an LPI inference call). **31% (summarization) / 73% (email) fewer edits** vs no-learning, ~3 LLM calls/round, interpretable. **Directly supports personalizing without per-user fine-tuning** — the synthesis's P3 and the case for deferring LoRA.
- **KTO `paper_15_kto`** (slide deck in `papers/`, *not* the original manuscript): KTO trains on **unpaired binary** desirable/undesirable labels (no preference pairs) — exactly the kept/edited/rejected signal eri produces. HALO value `v = λ_D·σ(β(r−z_0))` (desirable) / `λ_U·σ(β(z_0−r))` (undesirable), reward `r = log[π_θ/π_ref]`, reference point `z_0 = KL(π_θ‖π_ref)`. **Matches or beats DPO 1B–30B, significantly beats DPO alone at 7B/30B, survives discarding 90% of desirables, and can skip SFT at 13B/30B.** No β number stated in the deck (source it from the original paper). Imbalance handled by `λ_D·n_D/(λ_U·n_U) ∈ [1,1.5]`.
- **DPO `2305.18290`** (NeurIPS 2023, original): requires **paired** chosen/rejected data + a reference policy π_ref (= SFT model, or Preferred-FT surrogate if no SFT). Loss `−log σ(β·Δlog-ratio)`. **Paper default β = 0.1** (0.5 for summarization). The "use 0.01–0.02, not 0.1" guidance is the *Reference-Policy* `naacl.447` critique of that default, not DPO's own recommendation. KTO's unpaired binary fit makes it the better objective for eri's implicit signal.
